# 报告到路线图

`data/report/` 放意图审查与重构方案，各模块的 `ROADMAP.md` 放由此抽出的重构路线图，与 `TODO.md`、`STATUS.md` 同放。审查说清哪里偏，方案说清怎么拆，路线图把该拆的依赖按站排开、逐站落地。

## 输入与产出

- 输入：`data/report/evaluation/<模块>.md`（意图审查，偏移清单按严重度排）与 `data/report/plan/<模块>.md`（重构方案，模块拆分加待确认决策）。
- 产出：`<模块>/ROADMAP.md`，与 `TODO.md`、`STATUS.md` 同放。

## 哪些进路线图

路线图只列该消掉的依赖：互引的环，与单向的越层（聚合引服务、聚合引适配、引入口）。容器与内件的互认不算环——`workspace` 是 `workorder` 的上级容器，容器认内件、内件认容器是常态，写成一句话说明后跳过。文档与代码脱节不是依赖问题，另起一节，随站改。

## 输出格式

固定四段：抬头、站点、逐站、顺序。每站独立成 `##`，站内用短列表一行一字段，读的人扫一眼就知道这站改什么。

抬头一句目标加依据，再一句范围（哪些不算）与一句纪律（行为不变、三绿）。

站点是有序列表，一行一站：站名、类型（环 / 越层）、先后。

每站五行，一行一字段：

- 现状：一句话说谁引谁
- 证据：`file:line`
- 来路：引入它的提交哈希，哪条边先、哪条后
- 拆法：怎么拆，指回 plan 的待确认决策
- 判据：怎么算拆完

文档待改另起一站，字段用现状 / 拆法 / 判据 / 时机。

顺序一段收尾，写先后与清理项去处。范本见 `apps/qtcloud-work/src/cli/ROADMAP.md`。

## 步骤

1. 读报告：把 evaluation 的偏移清单与 plan 的模块拆分逐条读完，列出全部依赖问题。
2. 分环与越层：互引的记成环，单向越层的另记一站，容器关系剔除。
3. 追来路：成环的每条边用 `git log -S '<符号>' --oneline -- <文件>` 找引入它的提交，写清哪条边先有、哪条后接上；提交哈希与 `file:line` 都要落在站里。
4. 写站：一站一个问题，写现状（带 `file:line`）、来路（提交哈希）、拆法（指回 plan 的待确认决策）、完成判据。
5. 对齐报告：报告若同时改口径（如把某条从「环」降为「文档待改」），路线图的偏移编号与措辞跟着改，别让两边说法打架。
6. 分层提交：报告仓、放 `ROADMAP.md` 的代码仓、quanttide-work 指针、伞仓指针，逐层提交推送。

## 硬性约束

- 显式 pathspec：`git add -- <path>`，禁用 `git add -A`；动手前先 `git status -s` 摸底。
- 一条目一条发现，不嵌套；每条带 `file:line` 证据锚点，写不出锚点就不写。
- 命名归用户：目录、模块、术语不改，发现名不副实只写进报告、不自行改名。
- 行为不变：站里只搬依赖，命令面、输出信封、报错文字都不许改。

## 提交信息风格

- 报告仓：`report: <模块> 意图审查与重构方案（<日期>）`
- 代码仓：`docs: <模块> ROADMAP——<环>`
- quanttide-work：`chore: 更新 data/report 指针与 skill`
- 伞仓：`chore: 更新 <域仓> 指针`

## 完成后

汇报各层提交哈希与路线图路径，并指出报告里还没被路线图覆盖的偏移（清理项）。若伞仓还有其他落后指针，只提及、不擅自同步。
